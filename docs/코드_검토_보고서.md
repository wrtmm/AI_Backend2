## 프론트엔드

### 높음 — 로컬 게시글이 원격 페이지 결과를 밀어내 누락시킴

`frontend/src/App.vue:71-75`에서 1페이지는 localStorage 게시글을 원격 1페이지 앞에 붙인 뒤 6개로 자릅니다. 원격 API의 다음 페이지는 원격 게시글만 기준으로 offset을 계산하므로, 로컬 글이 하나라도 있으면 원격 1페이지의 마지막 글이 어느 페이지에도 나타나지 않을 수 있습니다. `total`에는 로컬 게시글 개수를 더해 페이지 수도 계산하므로 끝에 빈 페이지가 생길 수 있습니다.

**권장 조치:** 로컬 글을 페이지 처리 전에 원격 결과와 합쳐 일관된 목록으로 관리하거나, 원격 offset/limit과 로컬 항목 배치를 조정해 전체 목록에서 게시글이 빠지지 않게 합니다.

### 중간 — API 주소가 개발자 로컬 주소로 고정됨

`frontend/src/App.vue:4`의 `API_BASE`가 `http://127.0.0.1:8000`으로 고정되어 있습니다. 배포된 사이트를 방문하는 브라우저는 방문자 본인의 localhost에 접속하므로, 별도 호스트나 HTTPS 환경에서 API 요청이 실패합니다. 현재 `frontend/vite.config.js`에도 개발 프록시 설정이 없습니다.

**권장 조치:** 배포 환경 설정으로 API origin을 주입하거나, 배포 구성에 맞는 same-origin API 경로를 사용합니다.

### 높음 — 프론트 테스트의 요청과 화면 전환 기대가 현재 구현과 다름

`frontend/src/App.spec.js:11-14,28,42,57`은 `/posts`, `/user/login` 같은 상대 URL을 예상하지만 실제 `frontend/src/App.vue:4,68,98,119`는 절대 URL을 사용합니다. 또한 테스트 `App.spec.js:64`는 `.mode-switch` 버튼으로 가입 화면을 전환한다고 예상하지만 실제 화면은 경로 `/signup`으로 구분됩니다(`App.vue:23-25,196-206`). 테스트가 현재 구현 계약을 반영하지 않아 실패하거나 동작 회귀를 잡지 못할 가능성이 높습니다.

**권장 조치:** 테스트를 현재 라우팅 및 API 주소 구성과 일치시키고, 로그인/가입 전환과 실제 요청 URL을 검증합니다.

## 백엔드

### 높음 — JWT 비밀 키 누락 시 알려진 기본값으로 토큰을 서명함

`app/security.py:61-62`는 `JWT_SECRET_KEY`가 설정되지 않으면 공개된 고정 문자열을 사용합니다. 이 상태로 배포되면 제3자가 서명을 위조할 수 있습니다. 현재 보호된 API가 토큰을 사용하는 범위는 제한적이지만, 인증을 도입하는 즉시 영향이 커집니다.

**권장 조치:** 운영 환경에서는 비밀 키가 없거나 충분히 강하지 않으면 시작을 거부하고, 개발 환경의 기본값 사용은 명시적으로 분리합니다.

### 중간 — 가입에서 한 글자 비밀번호를 허용함

`app/routes/user.py:16-19`는 비밀번호 최소 길이를 1자로 제한합니다. PBKDF2는 저장된 해시 계산 비용을 높이지만, 사용자가 쉽게 추측 가능한 비밀번호를 고르는 것을 막지는 않습니다.

**권장 조치:** 제품 정책에 맞는 최소 길이 기준을 정하고 가입 입력에 적용합니다.

### 중간 — 저장된 해시의 PBKDF2 반복 횟수 상한이 없음

`app/security.py:20-29`의 `verify_password`는 해시 문자열에서 반복 횟수를 읽어 그대로 PBKDF2에 전달합니다. DB 값이 손상되거나 변조되어 과도하게 큰 값이 들어가면 로그인 요청 하나가 CPU를 오래 점유할 수 있습니다.

**권장 조치:** 반복 횟수에 유효 범위를 적용하고, 계산 전에 salt/digest 길이와 형식도 검증합니다.

- 저장된 해시의 변조 가능성 및 JWT 위조의 실제 영향 범위는 배포 환경과 향후 인증 미들웨어 구성에 따라 달라집니다.
